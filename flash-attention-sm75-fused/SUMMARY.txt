────────────────────────────────────────────────────────────────────────────────
CENTRAL HYPOTHESIS
────────────────────────────────────────────────────────────────────────────────

Can we keep the output matrix O and the score matrix S entirely inside WMMA
accumulator registers (wmma::accumulator), using warp shuffles (__shfl_xor_sync)
to compute softmax directly in the register file, eliminating all intermediate
shared memory stores for scores?

Answer: Yes. Fully validated and benchmarked.

────────────────────────────────────────────────────────────────────────────────
PHASE 0 — WMMA ACCUMULATOR LAYOUT VERIFICATION
────────────────────────────────────────────────────────────────────────────────

Tool: probe_layout.cu

The layout of wmma::fragment<accumulator, m16n16k16, float> on SM75 was
verified empirically. Each thread T in the warp (lane 0..31) holds 8 floats
mapping to two rows of the 16×16 output tile:

  group_id        = lane >> 2          (0..7)
  thread_in_group = lane & 3           (0..3)

  x[0] → C[group_id    ][ thread_in_group*2     ]   upper-left
  x[1] → C[group_id    ][ thread_in_group*2 + 1 ]
  x[2] → C[group_id + 8][ thread_in_group*2     ]   lower-left
  x[3] → C[group_id + 8][ thread_in_group*2 + 1 ]
  x[4] → C[group_id    ][ thread_in_group*2 + 8 ]   upper-right
  x[5] → C[group_id    ][ thread_in_group*2 + 9 ]
  x[6] → C[group_id + 8][ thread_in_group*2 + 8 ]   lower-right
  x[7] → C[group_id + 8][ thread_in_group*2 + 9 ]

Key property: each row of C[16][16] is owned by exactly 4 consecutive lanes
(group_id*4 .. group_id*4+3). Row-wise reductions require only XOR shuffles
with masks 1 and 2, without any cross-group communication.

Result: model CONFIRMED for all 256 elements. Shuffle reductions CONFIRMED
for all 32 lanes.

────────────────────────────────────────────────────────────────────────────────
PHASE 1 — WARP REGISTER SOFTMAX
────────────────────────────────────────────────────────────────────────────────

Tool: test_warp_softmax.cu

Implemented warp_softmax_unnorm() operating entirely on wmma::accumulator
fragment registers. Steps:

  1. Apply scale factor in-place (x *= scale)
  2. Compute per-row maximum using __shfl_xor_sync(mask, val, 1 and 2)
  3. Compute exp(x - max) in-place
  4. Compute per-row sum using __shfl_xor_sync
  5. Return RowMaxSum for online rescaling (do NOT divide — division deferred)

Validation results (vs CPU float32 reference):
  Normalized softmax (scale=1/sqrt(16)):  max_abs_error = 1e-8   PASS
  Normalized softmax (scale=1.0):         max_abs_error = 6e-8   PASS
  Unnormalized softmax (scale=1/sqrt(64)):max_abs_error = 6e-8   PASS

Zero shared memory accesses during softmax computation.

────────────────────────────────────────────────────────────────────────────────
PHASE 2 — FUSED KERNEL (flash_fused)
────────────────────────────────────────────────────────────────────────────────

Tool: flash_fused_kernel.cu

First complete fused kernel. Pipeline per KV tile per d_out:
  QK^T (WMMA) → softmax in regs → online rescaling in regs → P scatter to
  smem (half) → P@V (WMMA, accumulates directly into persistent O_acc)

Shared memory: 4 tiles × 512 B = 2048 B (2 KB) per block.
Persistent O_acc lives in registers across all KV tiles.
O never touches shared memory until the final store.

Validation: max_abs_error = 2.1e-5, max_rel_error = 0.049%  PASS

Benchmark (N=256, d=64):
  Latency:  0.040–0.053 ms
  TFLOPS:   0.020–0.026  (algorithmic)

Bottleneck identified: QK^T was recomputed once per d_out tile.
For d=64 (4 tiles), this meant 4× redundant QK computation.
True compute cost was 2.5× higher than algorithmically necessary.

────────────────────────────────────────────────────────────────────────────────
PHASE 3 — DIAGNOSIS AND OCCUPANCY ANALYSIS
────────────────────────────────────────────────────────────────────────────────

Tool: diagnose.cu

Isolated each pipeline stage:

  V0 (memory only):              0.167 ms   0.100 TFLOPS
  V1 (+ WMMA QK^T):              0.154 ms   0.109 TFLOPS
  V2 (+ softmax in registers):   0.175 ms   0.096 TFLOPS
  V3 (complete kernel):          0.191 ms   0.088 TFLOPS

Softmax overhead over QK:  +13.7%
PV + online + store:       +9.6%

Softmax in registers is NOT the bottleneck.

Occupancy analysis (V3: 96 regs/thread):
  Max blocks/SM by regs:  21  (66%)
  Blocks in grid (N=256): 16
  Blocks/SM average:      0.44

Primary bottleneck: grid too small. Only 16 blocks for 36 SMs.
20 SMs completely idle.

Solution identified: add batch and head dimensions to the grid (3D grid).

PHASE 4 — MULTI-HEAD GRID (flash_mha)

Tool: flash_fused_multihead.cu

Extended the kernel to grid = (N/16, H, B).
Each block still processes one 16-row query tile, one warp.

Sweep results (still with QK recomputation per d_out):

  B=1  H=1   N=256:    0.059 ms   0.267 TFLOPS   (sat:  5%)
  B=1  H=8   N=256:    0.060 ms   2.234 TFLOPS   (sat: 40%)
  B=4  H=8   N=256:    0.232 ms   2.319 TFLOPS   (sat: 68%)
  B=8  H=8   N=256:    0.335 ms   3.224 TFLOPS   (sat:100%)
  B=4  H=12  N=1024:   2.875 ms   4.482 TFLOPS   (sat:100%)

Multi-head grid confirmed as essential for GPU saturation.

────────────────────────────────────────────────────────────────────────────────
PHASE 5 — QK REUSE (flash_reuse_qk, flash_mha_reuse_qk)
────────────────────────────────────────────────────────────────────────────────

Tools: flash_fused_reuse_qk.cu, flash_mha_reuse_qk.cu

Critical architectural change: compute S = QK^T ONCE per KV tile, then reuse
the resulting P fragment for all 4 d_out tiles of the output.

Old loop structure (d=64, 4 d_out tiles):
  for d_out in [0,1,2,3]:
    recompute S = Q @ K^T          ← 4× redundant
    softmax(S)
    O[d_out] += P @ V[d_out]

New loop structure:
  S = Q @ K^T                      ← computed ONCE
  softmax(S)
  P materialized ONCE to smem
  for d_out in [0,1,2,3]:
    O[d_out] += P @ V[d_out]       ← P reused 4×

This eliminated the 2.5× redundancy factor for d=64.

Speedup (single-head, N=1024):
  Before: 0.698 ms   0.385 TFLOPS
  After:  0.147 ms   1.820 TFLOPS
  Gain:   4.75×

With multi-head grid (B=4, H=12, N=1024):
  flash_mha_reuse_qk: 2.875 ms   4.482 TFLOPS  (sweep)

Registers: 206–255 per thread (O_acc[4] kept alive simultaneously).
Occupancy: ~25% (8 warps/SM).

The QK reuse was the single most impactful optimization in the project.

────────────────────────────────────────────────────────────────────────────────
PHASE 6 — FLAT ARGS AND CODEGEN IMPROVEMENT (flash_mha_flatargs)
────────────────────────────────────────────────────────────────────────────────

Tool: flash_mha_flatargs.cu

Hypothesis: replacing struct-based kernel parameters with raw flat pointers
and __restrict__ qualifiers would reduce register count.

Result:
  Registers: 255 → 255  (no change)

However, performance improved significantly:
  Before (mha_reuse_qk): 3.758 ms   3.429 TFLOPS
  After  (flatargs):     2.591 ms   4.974 TFLOPS  (median)
  Speedup: 1.45×

The improvement came from better code generation (address calculation,
parameter passing, scheduler hints), not from reduced occupancy.

Robust benchmark (7 rounds × 200 iterations, B=4 H=12 N=1024):
  min:    2.503 ms   5.148 TFLOPS
  median: 2.591 ms   4.974 TFLOPS
  max:    3.311 ms

Sweep peak (saturated, B=4 H=8 N=2048):
  median: 6.828 ms   5.032 TFLOPS

This became the best full-attention kernel of the project.

────────────────────────────────────────────────────────────────────────────────
PHASE 7 — 2-TILE VARIANT (flash_mha_2tiles)
────────────────────────────────────────────────────────────────────────────────

Tool: flash_mha_2tiles.cu

Hypothesis: keeping only 2 O_acc fragments alive (instead of 4) would reduce
register pressure and improve occupancy.

Result:
  Registers: 255 → 255  (no change)
  The minimum live set of the algorithm already requires ~255 registers.
  The 16-register difference between O_acc[4] and O_acc[2] is absorbed
  by the compiler's existing allocation.

Performance (B=4, H=12, N=1024):
  2-tiles: 4.882 ms   2.639 TFLOPS
  flatargs: 2.638 ms  4.974 TFLOPS
  Speedup: 0.540×  (2-tiles is 1.85× SLOWER)

The 2-tiles variant recomputes QK 2× per q_tile (vs 1× for 4-tiles).
Since no occupancy benefit materialized, this extra compute was pure loss.

Conclusion: fewer output tiles does not help when the live set minimum
is already at the register limit. The bottleneck is algorithmic, not
incidental register allocation.

────────────────────────────────────────────────────────────────────────────────
PHASE 8 — 4-WARP BLOCK WITH SHARED K/V (flash_mha_4warp)
────────────────────────────────────────────────────────────────────────────────

Tool: flash_mha_4warp.cu

Architecture: 4 warps per block, 128 threads total.
  - Q: private per warp, preloaded once before KV loop.
  - K: loaded cooperatively by all 4 warps, shared across them.
  - V: loaded cooperatively per d_out, shared across warps.
  - O_acc[4]: private per warp, lives in registers.

Key insight: __syncthreads() creates liveness barriers that allow the
compiler to reuse register slots across barrier boundaries.

Register count:
  4-warp kernel: 86 registers/thread  (vs 255 for 1-warp flatargs)

Occupancy:
  regs/block = 86 × 128 = 11008
  smem/block = 12800 B
  Max blocks/SM by regs: 5
  Max blocks/SM by smem: 5
  Warps active/SM: 20  (62% vs 25% for flatargs)

Performance vs flatargs (B=4, H=12, N=1024, median):
  flatargs: 2.638 ms   4.974 TFLOPS
  4-warp:   3.378 ms   3.815 TFLOPS
  Speedup:  0.781×  (4-warp is slower)

Despite 62% occupancy vs 25%, the 4-warp kernel is slower because:
  1. __syncthreads() overhead: ~N/16 × 9 barriers per block for N=1024.
  2. The RTX 2070 L2 cache (4 MB) already absorbs K reloads in 1-warp kernel.
  3. Larger smem (12.5 KB) reduces blocks/SM via smem limit, not regs.

Only one case where 4-warp won: B=8, H=8, N=256 → 1.032× (within noise).

Conclusion: for SM75 with d=64, the 1-warp kernel with L2-cached K
outperforms the 4-warp kernel with explicit K sharing. The occupancy
improvement does not translate to throughput because the kernel is already
near the memory bandwidth ceiling, not the latency-hiding ceiling.

────────────────────────────────────────────────────────────────────────────────
PHASE 9 — V2: CAUSAL MASK + PING-PONG K (flash_mha_v2)
────────────────────────────────────────────────────────────────────────────────

Tool: flash_mha_v2.cu

Three features combined:
  A) Causal attention mask (lower-triangular)
  B) FP16 accumulator placeholder (template parameter, not benchmarked)
  C) Ping-pong double-buffering for K tiles

Register counts:
  flash_v2_kernel<CAUSAL=0>: 123 registers/thread
  flash_v2_kernel<CAUSAL=1>: 128 registers/thread

The ping-pong K buffer (2 × TN × D_FIXED halfs = 4096 B extra smem) reduced
register pressure from 255 to 123–128 compared to flatargs. This happened
because the alternating buffer index creates a liveness boundary that allows
the compiler to recycle register slots between K load and K use phases.

Smem: 7168 B (7 KB) per block.
Occupancy: 9 blocks/SM, 9 warps/SM, 28% (vs 25% for flatargs).

--- Feature A: Causal Attention ---

Causal tiles (kv_base > q_base + TM - 1) are skipped entirely.
Diagonal tiles apply per-element masking via apply_causal_mask().

Validation: PASS on all sizes tested.
  max_abs_error (causal): 7.1e-5   max_rel_error: 0.051%

Latency speedup (causal vs full):

  B=1  H=1   N=512:    1.05×   (small grid, overhead dominates)
  B=1  H=8   N=256:    1.28×
  B=1  H=16  N=256:    1.54×
  B=4  H=8   N=256:    1.62×
  B=8  H=8   N=256:    2.20×   ← best small case
  B=4  H=12  N=1024:   2.14×   ← best large case
  B=8  H=12  N=512:    1.85×
  B=1  H=16  N=2048:   1.86×
  B=4  H=8   N=2048:   1.90×

Theoretical maximum for causal: 2.0× (half the KV tiles are skipped).
Measured range: 1.05× to 2.20×.
Efficiency in saturated regime: 93%–107% of theoretical maximum.

TFLOPS causal (using half the algorithmic FLOPs as denominator):
  B=4  H=12  N=1024: 3.91 TFLOPS
  B=8  H=12  N=512:  3.81 TFLOPS
  B=1  H=16  N=2048: 3.85 TFLOPS
  B=4  H=8   N=2048: 4.02 TFLOPS

--- Feature C: Ping-Pong K ---

Effect on full attention vs flatargs:
  Small/medium cases (sat < 50%): slight improvement (hides global memory
    latency for the next K tile while computing current tile).
  Large saturated cases: neutral or slight regression (L2 cache already
    serves K efficiently; extra smem usage reduced blocks/SM marginally).

The ping-pong mechanism is more beneficial for d > 64 or hardware without
large L2 caches.

ROOFLINE ANALYSIS
────────────────────────────────────────────────────────────────────────────────

For d=64, the arithmetic intensity of the kernel (algorithmic FLOPs / bytes
moved from global memory) is approximately:

  Intensity = 4 N^2 d / (24 N^2) = d/6 = 64/6 ≈ 10.67 FLOP/byte

At 448 GB/s peak bandwidth:
  Memory roofline = 448 × 10.67 / 1000 ≈ 4.78 TFLOPS (algorithmic)

Best measured (flatargs, B=4 H=8 N=2048, best run):
  5.08 TFLOPS

This is above the simplified roofline estimate, consistent with the L2 cache
absorbing a portion of K reloads, effectively increasing the arithmetic
intensity beyond the global-memory-only estimate.

The kernel is operating in the memory-bandwidth-bound regime at peak load,
near the practical ceiling for this algorithm on SM75 with d=64.

────────────────────────────────────────────────────────────────────────────────
KEY TECHNICAL INSIGHTS
────────────────────────────────────────────────────────────────────────────────

1. The wmma accumulator register layout on SM75 is fully deterministic and
   exploitable at the software level. Per-row operations (max, sum, scale)
   can be performed without any shared memory round-trip.

2. The largest single optimization was architectural, not micro-level:
   computing QK^T once per KV tile and reusing the result for all d_out
   columns eliminated a 2.5× redundancy that dominated the original kernel.

3. Register pressure in single-warp WMMA kernels on SM75 is governed by
   the liveness of wmma fragments across the entire computation graph.
   The compiler cannot reduce below ~255 registers when O_acc[4] + S_acc
   + P_frag + all temporaries coexist in one warp's register file.

4. __syncthreads() barriers in multi-warp kernels create liveness boundaries
   that allow the compiler to recycle register slots, reducing registers from
   255 to 86. However, the associated synchronization overhead and increased
   smem usage offset the occupancy benefit for this problem size.

5. For SM75 with d=64 and a large L2 cache (4 MB), repeated loads of K
   tiles are absorbed by the cache. Explicit K sharing between warps or
   ping-pong buffering provides marginal benefit in the saturated regime
   but can help when the grid is small and latency hiding is needed.

6. Causal attention is implementable as a zero-cost compile-time template
   parameter. Fully-masked tiles are skipped with a single predicate check.
   Diagonal tiles apply per-element masking directly in the accumulator
   registers before softmax, preserving numerical correctness without any
   shared memory overhead.

7. The practical performance ceiling for this kernel on RTX 2070 is
   approximately 5 TFLOPS of algorithmic throughput for full attention
   and approximately 4 TFLOPS for causal attention, both achieved when
   the grid fully saturates the SM array.

────────────────────────────────────────────────────────────────────────────────
OPEN DIRECTIONS
────────────────────────────────────────────────────────────────────────────────

1. FP16 accumulator (USE_FP16_ACC=1): template ready, not benchmarked.
   Expected: up to 2× compute throughput at the cost of numerical precision.
   Relevant for inference workloads tolerating reduced precision.

2. Generalization to d=128: requires D_TILES=8, O_acc[8], higher register
   pressure. The ping-pong K approach may help more at d=128 since K tiles
   are larger and L2 reuse is lower.

3. Multi-query attention (MQA) and grouped-query attention (GQA): K and V
   are shared across multiple query heads. The 4-warp block architecture
   maps naturally to this pattern.

4. Sliding window / local attention: the causal tile predicate generalizes
   to arbitrary mask patterns with minor changes to tile_fully_masked().

5. SM80+ (Ampere) port: cp.async enables true asynchronous K prefetch,
   making the ping-pong pattern more effective. The WMMA layout changes
   slightly for m16n8k16.
